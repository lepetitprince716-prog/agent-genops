# 记忆与交接：记忆、状态、交接和任务库

agent 会话会结束、会压缩上下文、会被换掉。这页回答工作怎么活过这些：会话之间事实存在哪，
一个会话怎么交给下一个，并行的会话怎么共用一张任务清单，结果怎么汇报给我。

> **TL;DR**
> - 记忆是一个装小文件的目录，加一份每个文件一行的索引。里面的每条状态都是带日期的快照，动手前先对 git 或实机核一遍。
> - STATE 原地覆盖，保持简短。进度、决定、记忆日志只追加，带日期和作者。
> - 交接分三级：压缩前存检查点；到真实压缩窗口的 70% 时开接手会话；整段放弃时写完整交接再换人。
> - 会话树只留一层。任务状态只存在一个地方：共享任务库。
> - 汇报结论先行，坏消息不删。

## 记忆文件

1. **一个文件只放一条事实或一个紧密相关的主题；索引里每个文件一行。**
   理由：索引每个会话都会加载，文件按需才读。2026-07-22 把索引从 21.5 KB 压到 7.4 KB，连同其他几项一起，每次对话省下约 12,500 token。
2. **描述行里写清事实和出事的经过，很多时候只看索引就够了。**
   理由：agent 扫索引时，靠这行描述决定要不要打开文件。像「批量前先 smoke 一张（09-16 探针轮白占约 40 分钟）」这样的一行就够用。
3. **记忆里的每条状态都只是写下那天的快照。PR、分支、机器状态，用之前先对 git 或实机核。**
   理由：2026-09-17，一份云端会话写的交接说某条回环链路走的是隧道，还建议把启动定义改成固定别名。真实的定义会自动选路（当时走的是局域网）。照着改，自动选路就毁了。
4. **实时探测胜过任何快照。**
   理由：文档里写「某后端在线」，那是历史，不是现状。项目的权威顺序把实机、进程和日志放在所有文档之上。
5. **不留第二个真相源。**
   理由：2026-08-10 定了一套新的评级口径，特意没写进记忆，因为规则文件里已经有了。两份拷贝迟早对不上。
6. **记忆要分轮审计：合并重复、改写过期、修断链、压索引。**
   理由：记忆是一点点堆起来的。2026-09-18 一轮：63 个文件减到 59，合并 3 组重复，改写 2 条过期，断链为 0。2026-10-20 审了七个项目：主项目 217 条减到 160（索引 26.3 KB 减到 17.5 KB），第二个项目 68 减到 45，几个小项目合计 46 减到 25。删掉或压缩的文件都进带日期的备份目录。
7. **描述用将来检索时会用的语言写。**
   理由：2026-09-18 那轮审计保留了中文描述，没有全改成英文，因为召回靠的是中文说法。
8. **字少不等于省，如果省掉的是事实。**
   理由：2026-09-18 拿同一条记忆做了三个版本的盲测。现代中文 5/5；浅近文言也是 5/5，但汉字反而多了 48 个；激进文言 4.5/5，丢的半分全来自删掉的事实。
9. **派工路线的变化和 worker 退役，写进全局规则，不只写进某个项目的记忆。**
   理由：仓库主人的决定。项目记忆对别的项目不可见。
10. **退役的知识库要标成退役，不在上面接着建。**
    理由：仓库主人的决定。项目里留着一个退役目录，上面写着「不要读、不要引用、不要在它上面建逻辑」。

## STATE 快照和只追加的日志

11. **STATE 原地覆盖，只保留一份简短的「现在在哪」。**
    理由：仓库主人的决定。STATE 里没做完的工作只写指针（分支、PR、HEAD、交接目录），不写经过；经过写在带日期的交接目录里。
12. **PROGRESS、DECISIONS、MEMORY 只追加，每条带日期和作者标记。历史写错了就追加一条更正，不悄悄改。**
    理由：仓库主人的决定。改过的历史没法审计。
13. **路线图只写「下一步去哪、卡在哪道闸门」，不写进度数字。**
    理由：仓库主人的决定。进度归 STATE，路线图引用它。
14. **一个决定一旦做出，就写回它的权威文件，并从待决清单里删掉。**
    理由：仓库主人的决定，背后没有单次事故。
15. **没做完的不写成做完。**
    理由：仓库主人的决定。STATE 和路线图都对 UI 条目写着这条警告。
16. **写指针，不写会过期的状态；评审结论不放进被评审的那棵树里。**
    理由：2026-09-16，一份写着「四个包全部 PASS」的交接说明就躺在 PR 的 diff 里，下一个文档包因此按注入规则被拦下。评审结论只放在 PR 评论里。
17. **规划会话开工先读三样：STATE、路线图的状态表、runbook。**
    理由：仓库主人的决定。每个检查点验收完，收尾时往 PROGRESS 追加一条，更新 STATE 里那一条。

这些治理文件有固定的权威阅读顺序：现状、路线图、词汇表、决定、拓扑、路由表、脚本索引。两份打架时，以管这个领域的那份为准。

## 三级交接

能用轻的就不用重的。

| 级别 | 什么时候 | 留下什么 |
|---|---|---|
| 检查点 | 同一个会话，压缩之前 | 磁盘上一个文件，压缩后注入一次 |
| 接手会话 | 上下文到真实压缩窗口的 70%，或者任务关了但队列里还有活 | 一个很小的 JSON 提示，加任务库里的 notes |
| 完整交接 | 放弃这个会话 | git 收尾、一份成文的交接、一个已经启动的接手会话 |

三种的模板都在 [`templates/handoff.md`](../../templates/handoff.md)。

### 压缩前存检查点

1. 写检查点文件：目标和约束（含我否决过的）、带证据的已完成工作、失败的尝试、关键决定、没核实的假设、接下来一到三步、速查坐标。空的小节整段删掉。
2. 控制在 4 KB 以内，上限 10 KB。超了说明在写叙事。
3. 回复结尾写一句固定的锚点话，带上文件路径，压缩后的会话就知道要先读回来。
4. 可选：在 SessionStart 上挂一个匹配 `compact` 的 hook，把检查点注入一次（读完即删，两小时过期，最大 50 KB），然后归档。

18. **压缩摘要保留主线、丢掉细节，所以细节先落盘。**
    理由：丢的是准确的 `file:line`、命令原文、尝试失败的原因、我否决过的方案、下一步的第一个动作。少了这些，下一轮会把已经定下的事再争一遍。

### 70% 时开接手会话

19. **门槛按实际生效的压缩窗口算，不按模型名义上的窗口算。**
    理由：2026-10-14 查到，Opus 的窗口已经设成 50 万（大约 46.7 万就压缩），70% 的触发线却还按 100 万算。它一次都没触发过，所有 Opus 会话都掉进了自动压缩。50 万的 70% 约是 35 万。
20. **接手会话用全新上下文，不用 fork。**
    理由：fork 会把已经满了七成的上下文整个复制过去，等于没交接。
21. **接手提示只放一个 JSON 对象，`cwd` 和 `branch` 必填。**
    理由：2026-10-13，接手会话因为提示里漏了这两项找不到文件，翻了三遍 git。其他字段：`goal`、`next`（写动作，不写主题）、`files`（`path:line`）、`cmd`、`avoid`，再加一段不少于 80 个字符的背景说明。
22. **`avoid` 最值钱。死路要写成状态：写「闸门拒绝 X」，不写「试过 X，被拒了」。**
    理由：它让下一个会话不用把同一条死路再走一遍。
23. **接手会话只看 JSON、背景说明和任务库 notes，不读前任的记录，也不联系前任。**
    理由：2026-10-15 定下的。接手需要的东西全部写进 JSON 或 notes。早先的完整交接流程会传前任的会话 id，好让接手方去读记录；接手提示以较新的这条规则为准。
24. **发出接手会话后，前任结束本轮，不再动文件。两者共用 worktree 时不要归档前任。**
    理由：归档一个会话，会把共用它 worktree 的会话一起归档。

我这边是一个 Stop hook 从记录末尾算占用，超过门槛时每个会话只触发一次，把交接要求交回去，不会循环，永远以 0 退出。它必须注册成 managed hook，因为这里的用户级 hook 被策略拦下，而且不报错。

### 完整交接

1. 只有工作树有改动才做 git 收尾：在默认分支上就开一个主题分支，只暂存这次任务的路径，按约定写提交信息，PR 正文从文件读。半成品和没通过的工作不提交。
2. 交接文档按这些小节写：在做什么、哪些有效（带证据）、哪些没用以及原因、还没试的、文件现状、关键决定、卡点和待决问题、准确的下一步、环境。理想在 10 KB 以内，上限 30 KB。产物用路径引用，不贴全文。
3. 真正的后续工作做成提议卡片，每轮最多三张。
4. 先撤掉这条线上还没点开的接手卡片，再启动接手会话。

25. **执行方发现环境不对劲，就停下写交接，不提交。**
    理由：2026-07-04，执行方看到同一个提交有两个哈希，删分支能写进去、提交文件却写不进去。它没有提交，留下一份交接：问题、根因、位置、重放步骤、验收标准。部分写穿比完全隔离更危险。

## 会话树只留一层

26. **接手会话或交接出去的会话，启动后立刻 detach。**
    理由：2026-10-17 定下的。侧会话每结束一轮，应用就唤醒它的发起者；被唤醒的会话本轮结束又唤醒自己的发起者。链一深，每个祖先的上下文都要重读一遍。
27. **侧会话要自己再开会话之前，先把自己 detach。**
    理由：同上，这样它的子会话只向它汇报，不一路报到主会话。
28. **应用拒绝 detach 时（共用 worktree，或者是我手动放进去的会话），就改成每开一个会话立刻 detach 那一个。**
    理由：那些子会话有自己的 worktree。以后可能要开会话的会话，一开始就给它单独的 worktree。
29. **只有拥有这个任务的会话读侧会话的报告。**
    理由：一份报告解不开你自己任何一步，就不转发，对我最多提一行。

## 共享任务库

任务状态只存在一个地方：共享任务库（bd，也叫 beads）。聊天里的卡片、步骤列表、收尾框都只是它的视图。卡片一周过期，会话记录会被清理，任务库不会；而且非 Claude 的 worker 只看得到任务库。

30. **每个会话一个 actor，每条命令都带上：`<agent>-<模型>/<effort>#<会话短号>`。读不到的部分写 `unknown`。**
    理由：actor 各不相同，认领和关单的保护才起作用。shell 状态不跨调用，所以每条命令都要带。
31. **「领下一个」用 `ready --claim`，或者认领一个指定 id。不要随手收回别人的任务。**
    理由：两个并行的「领下一个」会话会领到不同的任务；写死 id 的卡片会被两个会话同时接走。租约五分钟过期，但只有有人跑 reclaim 才真的收回；确认会话已死，用 24 小时的门槛。
32. **交接时追加一条 work 记录：会话、分支、worktree、推没推、下一步、排除了哪些路径。接手方用 compare-and-set 把负责人换成自己。**
    理由：产物还没进 main 时，分支是找到文件的唯一线索（2026-10-13 那次）。负责人已经被别人改过时，compare-and-set 会以一个专门的退出码失败。
33. **等我拍板的任务设成 blocked，附一行卡点，不留在 in progress。**
    理由：2026-10-14 查到一个任务挂在 in progress，备注写着「不关单，等用户」，结果收工汇报里的待办清单是空的。我拍板之后，任务回到 open，负责人清空。
34. **关单时写元数据（agent、模型、effort、分钟数、会话数），关单理由第一句写结果。**
    理由：仓库主人的决定。有了元数据，「这活是哪一档干的」就能直接查。理由的第一句（60 字以内）会显示在侧边栏。
35. **新发现的工作要链回来源，带一个衍生链计数。第三个衍生任务一建好就设成 blocked。**
    理由：2026-10-07 定下的。同一类小修不会一个接一个自己滚下去，方向留给我定。
36. **每次收工汇报最后都列出 blocked 清单和两天没更新的 in progress 清单。只报，不动。**
    理由：仓库主人的决定。这两张单子是我需要、平时又看不到的。

标题：动词开头，24 个字以内，不写仓库名（标签里已经有了）。

## 汇报写法

37. **结论先行。第一句就说能不能用、为什么。**
    理由：读的人要在三秒内知道「能不能用、下一步做什么」。
38. **数字直接给：写「1952 过 / 26 挂」，不写「测试基本通过」。**
    理由：仓库主人的决定，背后没有单次事故。
39. **坏消息永远不删。没核实的、没做的、做不到的、挂了的都留着，并说清是不是自己弄坏的。**
    理由：仓库主人的决定。删的顺序是先删解释，再删细节，最后才合并条目。坏消息和命令不在可删之列。
40. **命令、路径、分支、链接一字不差照抄。被闸门挡住时，交出一条能直接跑的命令，不写一段说明。**
    理由：2026-09-19 起仓库主人的决定。命令要幂等，覆盖前先备份，找不到锚点就中止，并说明哪些部分没验证过。
41. **一个决定最多给两个选项，附上推荐。进度播报只在计划变了、出了故障、或者要长时间等待之前才写。**
    理由：篇幅对我是硬约束，进度播报也算进篇幅（2026-10-17）。

## 真实案例

- 2026-07-04：执行方看到漂移的 git 视图，停手留交接。对应规则 25。
- 2026-09-16：被评审的 diff 里放着评审结论，下一个包被拦。对应规则 16。
- 2026-09-17：云端写的交接看错了路由，还提议了一个破坏性的改法。对应规则 3。
- 2026-10-13：接手提示没有 `cwd` 和 `branch`，翻了三遍 git。对应规则 21。
- 2026-10-14：任务挂在 in progress，收工待办清单为空。对应规则 33。
- 2026-10-14：窗口改小后，70% 触发线一次没响。对应规则 19。

## 试过又放弃的

- 用文言或逻辑算子压缩规则和记忆：2026-09-18 放弃（规则 8）。
- 把上下文 fork 给接手会话：放弃（规则 20）。
- 按名义上的 100 万窗口算占用：2026-10-14 放弃（规则 19）。
- 接手会话去读前任的记录：2026-10-15 改成自带全部信息的提示。
- 「in progress，等用户」：2026-10-14 改成 blocked。
- 长会话只在开头注入一次上下文：它会像早期消息一样被冲淡。现在由一个 hook 重新注入，前 12 轮不出声（2026-08-25）。
