# 派工：谁来干，主会话怎么验收

这页回答四个问题：主会话什么时候才该把活交出去？哪类活给哪个 agent？任务包里写什么？
主会话凭什么认定结果是真的？

> **TL;DR**
> - 一条链能做完的活留在主会话。只有两种情况才派：并行铺开，或者不让大块阅读挤占主会话的上下文。
> - 选能兜住失败的最低一档：可核对的批量活给 Haiku，拿不准给 Opus medium，有契约要守给 Opus high。
> - 每个 worker 都拿一份任务包：一个目标、写入范围、不做什么、允许的命令、验收检查、RESULT 文件。
> - worker 自己说做完了不算验收。主会话回头读产物、重跑数字。
> - 并行写入时一个 lane 一个 worktree。往共享文件里合，由主会话一个一个串行合。

## 什么时候不派

主会话负责规划、派工、核验、记录。几步工具调用就能做完的活，它自己做。

1. **几步工具调用能做完的活，留在主会话。**
   理由：派一次活要写任务包、冷启动、再验收一遍，worker 还拿不到主会话的上下文。单链任务上，这些成本换不回任何东西。
2. **派工只有两个理由：并行铺开互不相干的 lane，或者把大块阅读挡在主会话的上下文之外。**
   理由：2026-07-26 起仓库主人的决定（按门槛派工）。长会话里最稀缺的是主会话的上下文。
3. **事实类问题自己读，不派 agent。**
   理由：有一轮验收里，第二个工具的预读挂住了，会话日志停在 2.5 KB，10 分钟没长。主会话直接读代码，找出了那个分错类的脚本。要的结果是事实（「这个符号存不存在」）时，grep 比重启一个不稳的 agent 快。
4. **同一个形状连失败两次，回到盘点，不做第三次。**
   理由：常见原因是缺了工具或没读文档，不是代码写错（仓库主人的决定，2026-08-27）。

## 档位梯子

规则：选失败了主会话还兜得住的最低一档。档位由主会话自己定，不等人点名。我点了模型和 effort，就派那一个；没有对应的 agent 定义，就照着相邻的复制一份，改 name 和 effort，等它加载，不拿别的档顶替。

| 档位 | 模型 / effort | 给它 | 不给它 |
|---|---|---|---|
| haiku-worker | Haiku 5.5 / medium | 批量阅读和摘要、抽取、分类、grep 与盘点扫描、格式转换、日志摘要、跑命令报结果、守着多路复用器里的 worker | 多步编码、设计判断、调试、沾安全的活、网络调研 |
| sonnet-worker | Sonnet 5.5 / high | 需要综合多个来源的调研、脏乱输入的抽取、要诊断失败原因的跑命令报结果、Haiku 结果没过核对后的重试 | 普通实现（给 Opus medium） |
| opus-worker-medium | Opus 5.5 / medium | 默认档：普通实现、调试、排查、并行 lane | 规则上没有禁区；lane 带契约就升一档 |
| opus-worker-high | Opus 5.5 / high | 多文件实现、设计判断、有契约要守的 lane | 机械活（浪费） |
| sonnet-worker-max | Sonnet 5.5 / max | Opus 或主会话已经定好设计后的编码；目标清楚、方向给定的长时间优化 | 开放式设计、目标模糊的活；设计不对时它停下来报告，不自己改设计 |
| plan-reviewer | Opus 5.5 / medium，只读 | 草案计划的独立评审：漏项、没核实的假设、难点，带 `file:line` | 写代码、改文件 |
| fact-checker | Sonnet 5.5，只读 | 提交或写总结之前，核对「代码做了什么」「测试过没过」「库支不支持」这类说法 | 自己下结论 |

现成的定义在 [`templates/agents/`](../../templates/agents/)。用 Claude Code 以外的 agent 时，看那里的 [README](../../templates/agents/README.md)，每个角色配多大的模型都写在表里。

5. **Haiku 的结果，主会话用之前一律核对；每个 Haiku 任务包的上下文控制在约 200K token 以内。**
   理由：Haiku 在 200K 附近会压缩上下文，API 计费下超过 100K 的提示价格是五倍（2026-10-09）。2026-10-19，一个 Haiku subagent 复制约 20,000 个 base64 字符，连续三次都只复制了 1,643 个。现在这种载荷由主会话自己分块推送，每块校验哈希。
6. **沾安全的活不给 Haiku。**
   理由：它的安全分类器会直接拒绝，没有退路，这个 lane 就断了。
7. **调研 lane 给 Sonnet，不给 Haiku。**
   理由：2026-10-08，四个 Haiku 调研 lane 有三个跑偏了题。
8. **worker 不调 advisor，也不再往下派。**
   理由：advisor 继承最强的模型，还会读 worker 的整段记录。测过一次：为了找两段文字里的重复，花了 7.7 分钟、102k token。孙一级的 agent 也绕过了主会话选的档位。
9. **Workflow 式的批量铺开，每个 agent 调用都写明一个非最强的模型。**
   理由：2026-10-15，一个文献复核 workflow 的 agent 继承了会话里最强的模型，把额度烧掉了。
10. **退出计划模式前跑 plan-reviewer；提交或给人写总结前跑 fact-checker。**
    理由：仓库主人的决定（计划评审从 2026-09-22 起）。有一份计划经独立评审找出九处问题，九处都成立，其中五处我回到源头亲自复核过。

## 用 herdr 派外部 worker

herdr 是给 coding agent 用的终端多路复用器，主会话用它驱动其他厂商的 agent。Claude 模型从不走它：它们只作为主会话的 subagent 运行。

| Worker | 用途 | 备注 |
|---|---|---|
| Cursor Composer 2.5 | 默认：编码和改文件的 lane、判断、评审、调研、第二意见 | 没有 effort 参数，effort 编在模型 id 里 |
| DeepSeek（经 pi） | 批量、机械的 lane，脚本化修改，数据收集 | 只在非高峰用；effort 必填 |
| OpenCode Go（经 pi） | DeepSeek 高峰时段或失败时的替补 | 额度独立 |
| Grok | 2026-10-13 起暂停，等我说可以再用 | 不派 |

11. **给 pi 类 worker 一定传 `effort`：跑命令报结果用 low，默认 medium，调试和设计评审用 high。DeepSeek 不用 xhigh 和 max。**
    理由：不传就是 max，最容易编造的那一档。
12. **每次起 DeepSeek 前先查是不是高峰，高峰就换 OpenCode Go。**
    理由：厂商定价页（2026-09-27 读）写的工作日高峰是 UTC 01:00-04:00 和 06:00-10:00，价格翻倍。
13. **编码会话的 shell 在沙箱里时，不要从它直接起 worker 的 CLI。**
    理由：2026-08-04 这样起的 worker 撞上嵌套沙箱，exit 71 退出。多路复用器服务在会话沙箱之外跑 worker。shell 不在沙箱里，就不会有这个问题；有沙箱又没有多路复用器，就把这条 lane 留在主会话里做。
14. **改了正在跑的 worker 的指令，一分钟后去看它真实的读写文件。**
    理由：2026-09-20 三条纠正一直排在 pane 的队列里，agent 一条都没收到，白下了约 4 GB。「已提交」可能只是「已排队」。
15. **这个任务开的 workspace 全部关掉。**
    理由：仓库主人的决定，背后没有单次事故。

## 任务包

不管是不是 Claude，每个 worker 拿到的任务包都是同一个形状。完整模板见 [`templates/task-packet.md`](../../templates/task-packet.md)。

```text
TASK_PACKET
objective: 一个具体结果
owned_paths: 准确的写入范围，或只读
context_paths: 允许读来做参考的文件
non_goals: 照抄我的红线（不动 git / 不装东西 / 不改网络……）
allowed_commands: 有边界的命令清单
acceptance: 准确的检查项和要交回的证据
return: 把 RESULT（≤30 行：状态、路径、退出码、证据、风险）写到 RESULT_FILE=<绝对路径>，然后回复 DONE
不再往下派；不要回滚别人的改动
```

16. **任务包里写明「你就是执行者」。**
    理由：本地复验的 agent 多次以为另有后台 agent 在干，就停在那里等。
17. **要接着干，就起一个写明模型的新 agent，不要给已经结束的 subagent 发消息。**
    理由：给结束的 subagent 发消息续跑，会丢掉它的模型设置，改用会话本身的模型。
18. **给执行方的大 brief 用固定骨架，交付前先让执行方自己的工具只读预读一遍。**
    理由：预读在一份重构 brief 里抓出 3 个 P1，下一份抓出 1 个 P1 加 5 个 P2，一份纯测试 brief 抓出 3 个 P1 加 7 个 P2。每一处都会把执行方带偏。
19. **委派的 runner 只执行；创作和参数上的决定都留在派工方。**
    理由：仓库主人的决定，每份 runner 的 runbook 里都写着：服装、LoRA 权重、adapter 强度和最终选图都归派工方。runbook 里还写着：先用打印模式看命令，素材报错原样转述并停下，报告里的每个路径都亲自打开过，交付不足就照实说。

## 主会话验收

20. **worker 的自述不算验收。**
    理由：仓库主人的决定。数字要对着产物或重跑结果核。`done` 才算定了，`unknown` 不等于做完。
21. **读 RESULT 文件，不读终端。**
    理由：终端里有启动横幅，白占上下文。退路依次是：会话日志里最后一条 assistant 消息，再不行就限定读最后 40 行。
22. **Haiku 的结果没过核对，换 Sonnet 重做，不再问 Haiku。**
    理由：仓库主人的决定，背后没有单次事故。
23. **测试类 PR 里，要有一个评审带着变异视角看。**
    理由：见下面的完整例子。「断言写得对」只是及格线，「实现改坏了这条测试会挂」才是测试的价值。

验收清单：

- [ ] RESULT 文件存在，不超过 30 行。
- [ ] 里面的每个路径都存在，主会话亲自打开过。
- [ ] 里面的每个数字都重跑过，或者从产物里读到过。
- [ ] 任务包里的每个验收项都有真实输出，不是一句声称。
- [ ] 没核实的项目标成没核实。
- [ ] workspace 已关；worktree 保留，除非我要求删。

## 并行 lane 不打架

24. **一个写入 lane 一个 worktree。只读的 lane 可以共用一个检出。**
    理由：2026-09-16，主检出里有 55 个改动文件，被当成孤儿改动封进 WIP 提交后切走了分支。其实它属于一个还活着的会话，那个 pane 的状态显示的是 done。
25. **多路复用器上最多同时三个 worker；排写入 lane 之前先跑双 lane 预检。**
    理由：仓库主人的决定。预检会拒掉 worktree 或 pane 有重叠的 lane。
26. **几个 lane 必须改同一个文件时，每个 lane 写一个片段文件，由主会话串行合入。**
    理由：仓库主人的决定。片段里放完整的插入文本和一个内容锚点，不写行号。每合一次就跑一次契约测试。
27. **删 worktree 之前，先扫一遍有没有从没进过任何分支的工作。**
    理由：2026-08-16，一个 worktree 里放着一整条 3D 线（16 个改动文件、10 个测试文件、一套工具链），从没进过任何分支；另一个 worktree 里有 255 MB 分析产物，主检出里没有副本。
28. **在同一个分支上建自己的 worktree 之前，先清掉 subagent 留下的 worktree；`cd` 失败就中止。**
    理由：有一次验收，`worktree add` 撞上残留失败，`cd` 也悄悄失败了，检查跑进了主检出，得出一个假结果。

## 先调研，再动手

29. **写代码之前，先盘点已经有的东西：MCP server 和插件、本机 CLI、项目里的设施、运行时版本。**
    理由：手写实现是最后一招。盘点结果缓存七天。
30. **然后按改动的分量去搜开源实现。**
    理由：仓库主人的决定。分三档：跳过（改一个字符串、一个参数、修一个已经定位的 bug）；轻量（单文件、不加依赖：快搜一次，一行汇报，然后动手）；完整（新模块、新依赖或架构变化）。拿不准就往重里走。
31. **完整档要给候选打分，写代码前先把对比表拿出来。**
    理由：仓库主人的决定。总分 = 契合度 ×3 + 维护 ×2 + 依赖分量 ×2 + 可读性 ×2 + 成熟度 ×1，满分 50。契合度低于 3 直接淘汰。star 数不算分。许可证有问题一票否决，被否决候选的 GPL/AGPL 源码不读进上下文。

盘点时的安装分档：项目内、可回退的安装直接装，事后说明；全局包给出准确命令然后停下；涉及凭据的，只写变量名和去哪里拿，不猜。

## 完整例子：一条纯测试 lane

规划用的主会话想给五个模块的核心判定逻辑补直接单测，源码一行不改。这条 lane 是这样跑的。

1. 事实底料。两个只读的 Sonnet subagent 分别列出每个目标的文件、行号、签名和分支行为，要求「只报事实，不给重构建议」。两份清单互相校验，主会话再自己读代码核一遍。
2. 范围裁决。主会话逐项决定钉住什么、排除什么，每项写理由。
3. 写 brief。固定骨架：定位与前置条件、背景事实（行号基线钉在一个具名的 main 提交上）、任务清单 T0（事实闸门）到 Tn、验收命令、PR 要求。验收里有一条「源码目录的 diff 必须为空」。
4. 预读。执行方自己的工具先只读预读 brief，找出 3 个 P1 和 7 个 P2。主会话改完才交付。
5. 执行。一个外部 coding agent 无头运行，沙箱允许写工作区，开了 PR，没有自己合。
6. 主会话做确定性核查：CI 真绿、测试数增量说得清、PR 正文带齐要求的证据、每条评审意见都处理过。
7. 三角验证。三个评审并行，每个都写明模型：对照 brief 的合规审查（Sonnet）、本地重跑测试和 lint（Sonnet）、第二个工具的只读评审。
8. 结果。两个 Claude 评审都跑绿了测试、逐条对过源码，判 CLEAN。第二个工具换了个问法：「代码坏了，这条测试会不会挂？」它找出六处松断言：只查 argv 尾部、用成员测试代替相邻断言、漏了一个分支、用集合成员判断（恒取 `[0]` 也能过）、漏了一个键、用 `>=` 代替精确计数。
9. 修复和定规则。一个 subagent 在隔离的 worktree 里收紧了断言。变异视角的评审从此成为测试类 PR 的必选项。下一个纯测试 PR 第一次用上它，又抓出三处。

同一条 lane 里还有一个坑：执行方报的测试数是 220 到 265（只算 `tests/`），主会话报的是 291 到 336（全量）。两边都对。验收数字要写明按哪个口径数。
