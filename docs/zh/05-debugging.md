# 调试：工作流图、运行时和远程渲染机

这页回答：出图失败、卡住、或者出了错的图，agent 先看哪里？
内容是一张症状表、经 SSH 驱动 Windows 显卡机的各种坑、「失败两次就重新盘点」规则，
以及 agent 被卡住时交给我的命令长什么样。

> **TL;DR**
> - 判活打队列接口，不 ping。ComfyUI 挂了不等于机器挂了。
> - 最贵的一类是静默出错：读实际提交的图谱，核块数，比图之前先清共享状态。
> - 共享服务上进程被污染了就重启，别花时间推理。
> - 远程 PowerShell 一律写成脚本文件交给 runner 发，不拼内联字符串。
> - 同一个形态失败两次就停下重新盘点。被卡住就交一条能直接跑的命令。

## 症状表

版本要紧：标着 0.27.1 或 0.33.1 的结论没在 0.42.1 上复核过，两台出图机 2026-10-20 起都是 0.42.1。

| 症状 | 可能原因 | 先查什么 |
|---|---|---|
| 图谱被拒：value not in list | 本地模型索引落后一代；文件没下完 | 线上服务 `object_info` 里的名字；盘上字节数 |
| 装完节点，新节点类型不在 | 服务没真重启，或者休眠后带着旧代码活下来 | 进程启动时间；`object_info` 里有没有这个节点 |
| 升级后节点包什么都没注册 | 节点包是给别的核心版本写的 | 启动日志；节点列表 |
| 升级 ComfyUI 后同 seed 像素变了 | 正常漂移（Anima 0.27.1→0.42.1 PSNR 28–37 dB），或者真回归 | 并排实例同 seed A/B；构图不变就是漂移 |
| 回滚后旧运行时起不来 | 0.42.1 迁移了界面数据库 | 恢复升级前备份的数据库 |
| 只有量化模型在 VAE 解码时 OOM | 量化后的 DiT 没法部分卸载 | 解码前显式卸模型、清缓存 |
| 服务死掉，没有 traceback，事件日志有驱动重置 | 桌面程序吃穿了 `--reserve-vram 1.0` | 调高 `--reserve-vram`：Box A 的前台程序约占 2.4 GB，所以设 2.5；你的按自己的前台占用来定 |
| `/free` 后显存不降；报 "Cannot set version_counter for inference tensor" | 部分加载的 INT8 ConvRot 挂了 LoRA（漏约 11 GB） | 停服务再起；`/free` 救不回来 |
| 没有作业却占着显存或提交内存；WinError 1455 | 崩掉的作业留下孤儿或僵尸 Python | 按命令行列进程；按监听端口或命令行杀 |
| 服务说显存够，作业照样 OOM | 服务报的空闲数不算别的进程；Box A 前台程序常驻约 2.4 GB | 厂商工具的总量减去服务自己的占用 |
| 作业「成功」但输出为空，或者重跑轮询到超时 | 整张图命中执行缓存（0.27.1 不带 client id 时历史里不列输出） | 按 prompt 查历史；换 seed |
| 重跑拿到别张图的像素 | 本地复用了缓存的文件路径 | 按 prompt id 从机器的历史里取文件 |
| 队列卡死 | 某个节点在等一个机器连不上的模型下载 | 服务日志；队列接口 |
| 训练卡在第 3 步，显存耗尽 | 一次性计划任务一起重新触发了 | 按前缀列计划任务 |
| 共享机上同 seed 两次结果不同 | 某个节点原地改了模型（IP-Adapter：平均像素差 16.55），或者 object patch 在 clone 之间泄漏 | 带 `free_memory` 释放；特殊节点后接一次不挂 LoRA 的普通采样 |
| 几个 agent 共用一台服务之后出黑图 | 进程级污染，来源没抓到 | 重启服务 |
| 出涂鸦，或者控制被静默忽略 | 块数不匹配 | 卡片的 `blocks`；补丁数 = 张量数 ÷ 3 |
| LoRA「兼容」但什么都没变 | 强度 0 被短路，或者键方言错了导致零补丁 | 日志里的补丁数；对照臂用 0.001 |
| 输出尺寸不对 | Qwen-Image 画布不是 16 的倍数 | latent 宽高 |
| 某条「发现」跟已知行为矛盾 | 图谱跟你以为的不一样（txt2img 带了 denoise 0.5） | 读 PNG 内嵌的图谱 |
| ping 全丢，机器「死了」 | ICMP 本来就封着 | 队列接口，或者 22 端口 SSH |
| system-stats 返回 500 | 只有它挂，queue、prompt、object-info 都是 200 | 判活用队列接口 |
| PCIe 读到 Gen3、BAR 256 MiB | 休眠或驱动更新后链路协商掉档卡住 | 先重启复测，再怀疑 BIOS |
| SSH 退出码 255 | 传输层失败；别的非零码说明命令已经在远端跑了 | 只有 255 才换路线重试 |

## 静默出错的规则

1. **读实际提交的图谱，不读脚本默认值，也不读 元数据 JSON。**
   理由：2026-06-25 一张 txt2img 图带着 denoise 0.5，得出三条假结论（其中有 VAE 和曝光那两条），后来全部撤回。

2. **共享服务上比两张图之前，先用 `free_memory` 清掉节点状态。**
   理由：2026-10-01 一个 IP-Adapter 节点原地改了 DiT 块，下一张同 seed 的普通图平均差 16.55。
   只卸模型洗不掉，清节点内存后逐像素恢复。那天两次误判都栽在这上面。

3. **自写节点替换模块前向时用 injection，不用 object patch。**
   理由：在 0.33.1 上，服务在同一底模的不同 clone 之间切换时不恢复 object patch，包装会漏进下一个
   不相干的作业。验收办法：特殊节点之后紧接着跑一次不挂 LoRA 的普通采样。

4. **长时间运行的共享服务出黑图：重启。**
   理由：2026-10-01 早上重启后约一小时，几个 agent 共用过这台服务，图生图又开始出黑图。干净进程就好了；精度是误导，
   为它做的 bf16「修复」已回滚。来源没抓到。

5. **不要为了拿回缓存输出给提交加 client id。**
   理由：加了会把进度广播变成单播，进度条就哑了。0.27.1 上同图重跑会轮询满 1800 秒超时，看着像挂死；
   正确修法是回查最近 200 条历史里同一个 prompt 的输出，查不到就立刻报错提示换 seed。

## 远程 Windows 机的规则

1. **PowerShell 写成脚本文件交给 runner 发，绝不拼内联字符串。**
   理由：Windows OpenSSH 默认 shell 是 cmd.exe，命令先过它的解析才轮到 PowerShell；UTF-8 灌进
   PowerShell 5.1 的 stdin 是有损的；cmd 的命令行上限 8191 字符。runner 把脚本编成 UTF-16LE
   base64 走 stdin。

2. **runner 负载保持小，大文件先拷过去。**
   理由：2026-10-01 在 Box A 上，60 KB 以上的脚本间歇卡死（1–46 KB 从没卡过），远端留下等 EOF 的
   PowerShell 进程。超时后按 pid 杀掉。

3. **按 PowerShell 5.1 的脾气写代码。**
   理由：下面每一条都栽过一次。调另一个脚本并抓输出要分两句写，别塞进带管道的括号表达式。
   临时脚本必须以 `.ps1` 结尾。用 `-LiteralPath`（PowerShell 会把文件名里的方括号当通配符，`Move-Item`
   报成功却什么都没动）。脚本开头设 `$ProgressPreference = 'SilentlyContinue'`。`Write-Host` 经 SSH
   会变成 stderr 上的 CLIXML 大块（2026-09-23），日志先收进列表，最后在顶层一次写出。
   函数里的 `Write-Output` 会混进返回值。

4. **控制台输出按 GBK 解码，状态认数字码。**
   理由：Box A 控制台代码页是 936（2026-08-27）。三周日志里有 40 多条乱码的「找不到文件」。
   `sc query` 的输出乱码之后数字还在，英文单词就没了。

5. **cmd.exe 单行命令只写最简单的，长一点就写成 CRLF 的 .cmd 文件。**
   理由：cmd 会吃掉 `;`、`$?`、`&&`、`<`。`if not exist DIR mkdir DIR & move ...` 会静默跳过 move。
   agent 的 Bash 工具会把 `>nul` 改写成 `>/dev/null`，到了 Windows 上就是一个不存在的路径。

6. **常驻进程用 WMI 进程创建拉起。**
   理由：SSH 会话是一个 job 对象，断开时整棵进程树一起杀；没有窗口站时 `Start-Process` 失败也不报错，
   连日志目录都不建。「改文件、停、起」拆成几个小脚本，合在一起容易挂。

7. **计划任务要想清楚再建。**
   理由：经 SSH 建的任务只在用户登录时运行；走 XML 要写 S4U 登录、UTF-16 带 BOM（2026-10-13）。
   一次性任务确认拉起后立刻删定义：2026-07-20 九个任务一起重新触发，训练卡在第 3 步。
   服务类任务正好相反，删定义会杀掉正在跑的实例，所以保留定义、把开始时间设成已过去的时刻。
   交互式任务弹出的窗口，有人会顺手关掉。

8. **加载 CIM 模块会挂的机器上，只用纯 cmd 或一句 WMI 调用，别加长超时。**
   理由：Box B 三周里超时 14 次，卡住的进程最后连 SSH banner 都堵住了（2026-10-13）。

9. **远程删除绝不走回收站。**
   理由：2026-10-13 实测，非交互 SSH 会话里调回收站 API 等于永久删除。改成移进同盘带日期的隔离目录，
   写一份恢复映射，由我自己删目录。

10. **远程脚本不碰代理设置。**
    理由：Box B 配的代理是死的，改默认 web 代理会让会话挂住、留下孤儿进程。作业因为这个代理装依赖失败时，
    报告出来，不改作业里的代理变量（2026-10-19）。

11. **信监听端口查询，不信服务日志；按端口或命令行杀进程。**
    理由：有些服务绑了全部网卡，日志里却永远打印 127.0.0.1。`taskkill /im` 会误杀别人的同名进程，
    还留下 multiprocessing 子进程。

12. **hook 改坏了工具输出的形状，是工具缺陷，不是网络问题。**
    理由：2026-10-19 一个托管的 post-tool hook 报 "expected object, received string"，把一个根本没跑的
    脚本的输出藏了起来。换一次调用形状；还不行就把命令交给我。

## 失败两次就重新盘点

1. **同一个任务失败两次就停下，不做第三次同形尝试。**
   理由：常见原因是缺工具或没读文档，不是代码写错。2026-08-27 起仓库主人的决定。

第二次失败后的步骤：

1. 记下两次尝试和原样报错。
2. 重新盘点：手上有哪些工具和 MCP、项目里关于这件事的脚本和文档、实际在用的运行时版本（按 venv、按机器）、
   上次能用之后改了什么。
3. 核对计划背后的那条假设。错过的例子：「这台机器没装 triton」（训练 venv 确实没有，ComfyUI venv 有）；
   「机器缺这个功能」（装的浏览器扩展落后两个版本，2026-08-25）；「网络策略禁止这个调用」
   （发一个最小请求就通了，2026-09-16）。
4. 换一条路，或者停下来报告卡点。

## 被卡住时交一条能跑的命令

1. **被卡住就交能跑的命令，不交一段说明。**
   理由：2026-09-19 起仓库主人的决定。闸机、缺权限、root 所有的文件、只能在图形界面做的一步，都会让
   agent 停下；只描述步骤等于让我自己拼。

常见卡点：加载或重启 launch agent、托管会话跑不了的进程和网络探针、要占出图机的图形界面加载验证、
任何网络控制面的改动。

- [ ] 一条命令，最短形式，能直接复制粘贴。
- [ ] 幂等：跑第二遍什么都不变。
- [ ] 覆盖的文件先备份。
- [ ] 找不到要改的锚点就中止。
- [ ] 先在副本上验过。
- [ ] 写明哪些部分没验证。

大致形状（示意）：

```bash
set -euo pipefail
f="$HOME/example/service.yaml"
grep -q '^args:' "$f" || { echo "anchor 'args:' missing, abort"; exit 1; }
grep -q -- '--reserve-vram 2.5' "$f" && { echo "already applied"; exit 0; }
cp -p "$f" "$f.bak.$(date +%Y%m%d%H%M%S)"
# 这是 macOS 的 sed 写法；GNU sed 去掉 ''
sed -i '' 's/^args:\(.*\)$/args:\1 --reserve-vram 2.5/' "$f"
grep -- '--reserve-vram 2.5' "$f"
```

## 真实案例

- **2026-07-02，假重启。** 服务重启 0.5 秒就返回，Python 进程还活着，新装的节点包一直没加载。
  规则：先杀监听进程再启动，然后核启动时间。
- **2026-07-20，任务重新触发。** 九个一次性计划任务一起跑起来，显存耗尽，训练卡在第 3 步。
  规则：一次性任务拉起后删定义；收尾时按前缀查一遍，必须为空。
- **2026-08-25，孤儿进程。** 13 个孤儿 multiprocessing Python 占了 33 GB，一份验证过的配置起不来，
  报错还是误导性的 "invalid python storage"。规则：核对监听者的身份，不能只看「端口活着、版本对」。
- **2026-08-28，传了别名没传 URL。** 请求助手拿到的是机器别名而不是解析后的 URL，拼出一个假主机名，
  出网代理回了 403。为此白派了一次网络专家。规则：那里的 403 是调用写错了。
- **2026-09-01，PCIe 误判。** 链路读到 Gen3、BAR 256 MiB，agent 推断是 BIOS 或线缆问题。
  BIOS 一直没问题，重启一次就回到 Gen5 x16、BAR 16 GiB。
- **2026-09-30，像素张冠李戴。** 先 A 再 B，再重跑 B，存下来的是 A 的像素配 B 的元数据（Box B，0.27.1）。
  规则：按 prompt id 从机器的历史里取输出；本地缓存路径复用已删除。
- **2026-10-01，一天两次误判。** Box A 上的对比是在 IP-Adapter 和 dtype 节点动过共享进程之后跑的。
  规则：任何对比前先清节点内存。
- **2026-10-13，回收站是永久删除。** 远程清理调回收站 API，磁盘空间立刻变大，回收站里什么都没有。
  规则：移进隔离目录并写恢复映射。

## 试过放弃的

- 给提交加 client id，让缓存输出出现在历史里。
- 为 CIM 挂起加长超时。
- 改精度来治黑图。
- 远程回收站删除。
- 经 SSH 拼内联 `powershell -Command` 字符串。
